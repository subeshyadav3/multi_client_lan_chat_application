🗺️ High-Level Project Overview & Data Flow

🌐 Berkeley Sockets & TCP/IP Deep-Dive

What is a Socket?
In UNIX/Linux systems, "everything is a file". A socket is an operating system abstraction representing an endpoint of network communication. When you call socket(), the kernel allocates a file descriptor (an integer index into the process's file descriptor table) and creates internal network send/receive ring buffers in kernel space.

1. The Server Socket Lifecycle

  1. socket(AF_INET, SOCK_STREAM, 0): Allocates an IPv4 (AF_INET) TCP (SOCK_STREAM) socket descriptor.
  2. setsockopt(..., SO_REUSEADDR, &opt, sizeof(opt)): Critical Systems Call! When a TCP server shuts down, sockets remain in the TIME_WAIT state for 1–2 minutes to ensure lingering in-flight packets expire. SO_REUSEADDR allows the server to immediately re-bind to port 8080 upon restart without getting Address already in use (EADDRINUSE).
  3. bind(server_sock, (struct sockaddr*)&addr, sizeof(addr)): Binds the socket to all local network interfaces (INADDR_ANY) and port 8080 (converted to network byte order via htons(8080)).
  4. listen(server_sock, MAX_CLIENTS): Transitions the socket from active to passive listening mode. The kernel creates two internal queues:
    • SYN Queue (Incomplete Connection Queue): Holds TCP connections in the process of 3-way handshaking.
    • Accept Queue (Completed Connection Queue): Holds fully established connections waiting for the application to call accept().
  5. accept(server_sock, ...): Extracts the first completed connection from the Accept Queue, allocates a new dedicated socket descriptor for that specific client, and leaves server_sock free to continue listening.

2. Byte Stream vs Message Boundaries (TCP Stream Fragmentation)

The Fundamental TCP Trap: Why You Cannot Assume 1 send() == 1 recv()

TCP is a continuous byte-stream protocol with no intrinsic concept of "messages" or "packets" at the application layer. The underlying network layer (IP packets, MTU, router fragmentation) splits and bundles bytes based on network conditions.

  • Packet Splitting: A single send() of 100 bytes may arrive across three separate recv() calls of 30, 50, and 20 bytes.
  • Packet Coalescing (Nagle's Algorithm): Two quick send() calls may be merged into a single recv() buffer.

ConnectHub's Solution: We use newline-delimited framing (\n). Both server/connection.c and client/client.c implement a line accumulator buffer. The thread loops over raw received bytes, accumulating them until a \n byte is found, guaranteeing that only complete, discrete command lines are parsed.

🔒 Concurrency, POSIX Threads & Locking Theory

Why POSIX Threads on the Server?
Each connected client on the server has independent state, blocking network operations, and bursty message patterns. Spawning a lightweight POSIX thread (pthread_create) per connection provides isolated execution stacks while sharing the process address space for instant, zero-copy data routing between users.

1. Thread Detach Policy (pthread_detach)

In standard POSIX threading, a terminated thread remains in a zombie state until another thread calls pthread_join() to collect its return value, leaking thread stack memory if left unjoined. In ConnectHub, the server calls pthread_detach(pthread_self()) immediately upon thread entry in handle_client(). This tells the Linux kernel scheduler to automatically reclaim all thread descriptor and stack memory as soon as the thread exits.

3. Deadlock Prevention: The "Never Hold Lock During send()" Rule

How Deadlocks Happen & How ConnectHub Prevents Them

A classic concurrency deadlock occurs when Thread A holds Lock 1 and waits for Lock 2, while Thread B holds Lock 2 and waits for Lock 1 (Cyclic Wait).

In network servers, a more subtle deadlock occurs: if Thread A locks client_mutex and calls send() on Client B's socket, and Client B's TCP buffer is full, send() blocks. While Thread A is blocked waiting for network I/O, no other client thread can log in, log out, or send messages because client_mutex is held!

ConnectHub's Snapshot Pattern:

// 1. Acquire mutex lock
pthread_mutex_lock(&client_mutex);

// 2. Take local stack snapshot of recipient socket descriptors
int target_fds[MAX_CLIENTS];
int count = 0;
for (Client *curr = client_head; curr; curr = curr->next) {
    if (strcmp(curr->current_room, target_room) == 0) {
        target_fds[count++] = curr->sockfd;
    }
}

// 3. RELEASE MUTEX IMMEDIATELY
pthread_mutex_unlock(&client_mutex);

// 4. Perform network I/O outside critical section
for (int i = 0; i < count; i++) {
    send(target_fds[i], message, strlen(message), 0);
}

⚡ I/O Multiplexing (select()) & Terminal Raw Mode (termios)

Why Single-Threaded select() on the Client?
Writing a multi-threaded terminal client often causes severe UI corruption: if the background network thread prints an incoming message while the user is typing, the terminal cursor jumps and mangles the input box. Using a single-threaded select() loop eliminates the need for display locks while keeping the interface 100% non-blocking and responsive.

1. How select() Multiplexing Works

The select() system call monitors multiple file descriptors simultaneously to determine if any are ready for reading, writing, or have exceptional conditions.

+---------------------------------------------+ | select(maxfd + 1, &rfds, NULL, NULL, &tv) | +----------------------+----------------------+ | Blocks until an event occurs or 100ms expires | +----------------------------+----------------------------+ | | v v FD_ISSET(STDIN_FILENO) FD_ISSET(sockfd) Keyboard keystroke typed! Server data arrived! -> read_from_stdin() -> read_from_server() -> Updates input buffer / runs slash cmd -> Parses message & appends to chat | | +----------------------------+----------------------------+ | v Timeout (100ms tick) -> files_try_send_chunk() (streams file slices) -> clears expired typing indicators -> tui_draw() (refreshes terminal display)

2. Terminal Raw Mode with termios.h

By default, Linux terminals operate in canonical mode (cooked mode) with echo:

  • Input is buffered line-by-line by the kernel TTY line-discipline until the user presses Enter.
  • Keystrokes are automatically echoed to stdout.

ConnectHub disables canonical mode in client/tui.c:

struct termios raw;
tcgetattr(STDIN_FILENO, &orig_termios); // Save original settings
raw = orig_termios;
raw.c_lflag &= ~(ICANON | ECHO);        // Disable line buffering & auto-echo
raw.c_cc[VMIN] = 1;                     // Read returns immediately with 1 char
raw.c_cc[VTIME] = 0;                    // No read timeout
tcsetattr(STDIN_FILENO, TCSAFLUSH, &raw);

This gives ConnectHub full control over every keystroke, enabling:

  1. Password Masking: Printing * instead of typed characters during login.
  2. Arrow-Key History: Intercepting ANSI escape sequences (\033[A / \033[B) to scroll through past commands.
  3. Live Typing Indicators: Emitting typing notifications as soon as any key is touched.

🔑 In-House Cryptography (SHA-256) & Base64 Encoding

Zero Dependency Cryptography
Rather than linking heavy external libraries like OpenSSL or libcrypto, ConnectHub implements SHA-256 and Base64 entirely from scratch in C, demonstrating pure systems-level algorithmic understanding.

1. Step-by-Step SHA-256 Algorithm (NIST FIPS 180-4)

  1. Message Padding: The input string is padded so its bit length is congruent to $448 \pmod{512}$. First, a single 1 bit (0x80) is appended, followed by 0 bits. Finally, a 64-bit big-endian integer representing the original message length in bits is appended, making the total block size a multiple of 512 bits.
  2. Initialization: Eight 32-bit state registers ($H_0 \dots H_7$) are initialized with the fractional parts of the square roots of the first 8 prime numbers (2 to 19).
  3. Message Schedule Expansion: Each 512-bit block is expanded into 64 32-bit words ($W_0 \dots W_{63}$) using bitwise rotations and XOR operations ($\sigma_0, \sigma_1$).
  4. 64 Compression Rounds: The 8 state registers are scrambled through 64 rounds using round constants $K_t$ (cube roots of the first 64 primes) and bitwise functions:
    • $\text{Ch}(e, f, g) = (e \land f) \oplus (\neg e \land g)$
    • $\text{Maj}(a, b, c) = (a \land b) \oplus (a \land c) \oplus (b \land c)$
    • $\Sigma_0(a) = \text{ROTR}^2(a) \oplus \text{ROTR}^{13}(a) \oplus \text{ROTR}^{22}(a)$
    • $\Sigma_1(e) = \text{ROTR}^6(e) \oplus \text{ROTR}^{11}(e) \oplus \text{ROTR}^{25}(e)$
  5. Digest Output: The resulting state registers are concatenated to produce a 256-bit (64-character hexadecimal) hash digest.

2. Base64 Encoding Bit-Math Mechanics

Because the wire protocol is line-oriented ASCII using | and \n delimiters, transmitting raw binary files (which contain arbitrary 0x00, 0x7C, and 0x0A bytes) would corrupt protocol parsing. Base64 translates 3 binary bytes (24 bits) into 4 safe ASCII characters (6 bits each):

Binary Bytes: [ Byte 0 ] [ Byte 1 ] [ Byte 2 ] Bit Stream: [ 7 6 5 4 3 2 ] [ 1 0 7 6 5 4 ] [ 3 2 1 0 7 6 ] [ 5 4 3 2 1 0 ] 6-bit Chunks: [ Chunk 0 ] [ Chunk 1 ] [ Chunk 2 ] [ Chunk 3 ] Base64 Chars: 'A'-'Z', 'a'-'z', '0'-'9', '+', '/' (with '=' padding)

📦 Token-Guarded Chunked File Transfer Subsystem

Why Server-Mediated File Transfer?
Direct peer-to-peer file transfer requires hole-punching and complex NAT traversal. ConnectHub routes file chunks through the server, allowing file transfers across different subnets while enforcing strict access control, token verification, and server resource limits.
